# AI Secure / AIセキュア — 製品設計書 v0.1

作成: 2026年9月12日 / 状態: ローカル検証用プロトタイプ

## 1. 実現したい未来

**企業のセキュリティ担当者が、数百の警告を読んで推測するのではなく、対応する理由・確認事項・業務影響まで一つの画面で理解し、必要な判断を早くできる状態をつくる。**

製品の主語は「AIが守る」ではなく「担当者が、証拠に基づいて適切に動ける」です。AIを足したチャット画面や、危険度スコアを並べるだけの製品にはしません。最初の対象は、外部保守接続があり、専任SOCの人員が限られる企業・その運用受託事業者です。この顧客仮説は未検証です。

タグライン: **Evidence before action. 判断の根拠は手元に、操作の権限は人に。**

## 2. 今回の発表から取り込む要件

デジタル庁の2026年9月11日発表は、GSSでのVPN脆弱性を経由する不正アクセスと、職員等の個人情報約24.6万件が漏えいした可能性についてのものです。[S1]

公式Q&Aによれば、当初の深刻度評価はMediumで、公表済みの脆弱性が修正前に悪用されました。具体的な脆弱性は非公表です。[S2]

この発表は、AIが原因の事故を示すものではありません。また、公開情報だけで、本製品ならこの事案を防げたと証明することもできません。デモの機器名・ユーザー・CVE風参照・CVSS・イベント数・時刻はすべて架空設定です。

| 公開情報から得る論点 | 製品としての設計判断 | v0.1の実装 |
|---|---|---|
| 接続機器の脆弱性への対処 | 数値だけでなく、外部公開と到達経路を重ねる | 入力台帳からP1/P2/P3を判定 |
| 保守アカウントでの大量参照 | 認証とファイル参照を同じ主体・セッションで関連付ける | 3種類のスナップショットを相関 |
| 侵入経路・影響範囲の調査 | 観測事実、仮説、未確認事項を分ける | 根拠ID、仮説、外部送信未確認を表示 |
| アカウント停止と通信遮断 | 操作前に対象・業務影響・復旧方針を確認する | 承認付きシミュレーションのみ |
| 脆弱性管理の見直し | 継続的な資産確認と対応責任者・期限を管理する | 資産の古さ・不明項目を表示。運用管理の拡張は未実装 |

## 3. 何を売る製品か

製品カテゴリーは、**外部保守アクセスの侵害兆候を、証拠付きの初動対応へつなぐ運用支援**です。

「企業のあらゆるサイバー攻撃を防ぐ万能AI」「VPNの代替」「EDRやSIEMの置き換え」から始めません。既存のログ基盤・アクセス制御と協調し、情報が分かれているために担当者の判断が遅れる部分を狙います。『根拠を確認 → 業務影響を理解 → 必要な人が承認 → 操作の成否を検証』が中心体験です。

差別化候補は、関連付けの精度、日本語での初動手順、委託先保守への適合、データを顧客環境に残す構成です。ただし市場優位性や競合不在を確認済みという意味ではありません。汎用名称「AI Secure」の商標・類似名称も未調査です。

## 4. 核になるUX

### 最初の画面

大量の赤い警告ではなく、確認すべき上位の事案を表示します。カードに、関連する経路、入力時刻、根拠ID、事実・仮説・未確認、対応計画への入り口を配置します。P1は「すぐ確認すべき優先度」であり、攻撃確率や漏えい確率ではありません。

v0.1では全画面に「架空データ / 手動入力」「スナップショット」「実環境接続 0/3」「実操作なし」を表示します。接続されていないものを「保護中」と見せないことを優先します。

### 代表的なデモ

外部公開・未修正のVPN機器が台帳にある。非管理端末・未承認条件の特権ログインの後、同じユーザー・セッションが130個のファイルを短時間に参照。42個には機密ラベルがある。

画面は「保守アカウントの侵害を疑う相関候補」を表示する。ただし「VPNの脆弱性が悪用された」「外部に130件漏えいした」とは断定しない。元ログ・作業申請を確認し、失効計画の対象と影響を読む。v0.1の承認は記録とシミュレーションにとどまり、封じ込め完了を表示しない。

### 対応シート

根拠 → 対象 → 業務影響 → 事前確認 → 復旧方針 → 承認理由 → 明示確認の順。5分で失効し、入力が更新されれば古い承認は拒否します。実際に止める能力のない版なので、ボタンにも「シミュレーション」を明示します。

## 5. 検知を数学的な契約にする

### 資産優先度

E = 外部公開あり、V = 修正待ち、K = 既知の悪用ありと入力、R = 特権へ到達、D = 機密情報へ到達。

```text
P1_candidate = E ∧ V ∧ (K ∨ (R ∧ D))
```

CVSSがMediumでもE/R/Dが重なるならP1候補です。未知の真偽値はfalseに置き換えず、不明として別表示します。閾値は本製品の初期ポリシーであって、普遍的なリスク評価式ではありません。実際のネットワーク到達性を測る機能はまだなく、台帳の入力に依存します。

将来は、公式の既知悪用カタログやベンダーアドバイザリーでKを裏付けます。KEVは実際の悪用情報に基づくカタログとして有用ですが、未掲載なら安全という意味ではなく、GSS事案の脆弱性が掲載されていたと推測もしません。[S6]

### ファイル参照と相関

```text
N(u,s,a,t) = | { file_id : actor=u, session=s, asset=a,
                         t-300秒 <= event_time <= t } |
Bulk = N >= 100
```

同じユーザーu・セッションs・保存先aに対し、異なるファイル数を数えます。同一イベントの再送と同一ファイル再参照で件数を水増ししません。

相関は、直前30分以内の同一主体・セッションの成功ログインが特権利用であり、「端末非管理または作業未承認」、かつ台帳上の公開・未修正機器と関連し、機密ファイルを含む大量参照がある場合にP1候補とします。対応不能なセッションIDを推測でつなぎません。

最も多い窓を使う簡易方式で、低速な持ち出しや分散した参照、複数段階の高度な侵入は対象外です。正常なバックアップも大量参照に該当します。正常ログでの評価なしに閾値を本番適用してはいけません。

### 対応状態機械

```text
proposed/pending
   ├─ 5分経過 → expired
   ├─ 入力更新 → 承認拒否（再計画）
   └─ 人の明示承認 → approved（監査イベント）
                           └─ simulated / executed=false
```

本番版では、別権限の実行器、機器からの成否確認、検証済みの復旧手順を追加した後に、executing → verified / failed / recovery_required の状態を別途設計します。実行APIがHTTP 200を返しただけで封じ込め完了としません。

## 6. 責務を小さく分ける

```text
Collector → Normalizer → Detector → Case/Policy → Approval → Responder
                             │                           │
                             └→ Explainer（権限なし）    └→ Audit
```

| 部品 | 責務 | 保持してよい権限 |
|---|---|---|
| Collector | 認証・機器・ファイル参照ログの取得 | 読取専用。初期版は手動JSON |
| Normalizer | スキーマ検証・機微情報削減・仮名化 | 入力処理のみ |
| Detector | 再現可能な検知と相関 | 分析のみ |
| Explainer | 日本語での説明・未確認事項の整理 | ツール実行不可 |
| Policy | 事前に許可された対応計画の選択 | 本番資格情報を持たない |
| Approval | 人の承認、期限、入力バージョン整合 | 認証された承認操作のみ |
| Responder | 限定された対象・操作を実施 | 初期版は権限なしのシミュレーター |
| Audit | 操作の記録と検証 | 本番では独立した書込経路へ分離 |

今回のコードはPython標準ライブラリで検証を始めやすくしています。Astraなどからの再利用を前提とした境界は維持しますが、既存リポジトリやRustコアへの変更は行っていません。将来、軽量収集器や高頻度の検知器をRustに置き換える場合も、スキーマと権限契約を先に固定します。

Astraへ統合するとしても、最初は検知結果を読むだけの連携に限定します。Astraの自然文指示からVPNやIdPの管理資格情報へ直接アクセスさせない構成にします。

## 7. AIをどこで使うか

初期版はテンプレート説明が既定です。任意のローカルLLMへは、短い事実と参照IDだけを渡します。モデルに原文ログを命令として読ませず、ツールを与えず、出力の参照ID・形式・長さを検証します。プロンプトインジェクションは入力を命令と誤認させるリスクであるため、プロンプトの文面だけでなく権限分離を防御の中心にします。[S4]

本番のAI価値は、複数事案の共通点の説明、関係者別の報告文、機器別手順の整理、根拠付きの不足情報の指摘へ拡張します。勝手に危険度を下げる、アラートを消す、認証情報を取得する、例外許可を書き換える機能は持たせません。未実装の将来機能です。

## 8. セキュリティ要件

ゼロトラストは、内部ネットワークや所有関係だけで暗黙に信頼せず、リソースへのアクセスに認証・認可を求める考え方です。製品名や構成の宣言だけで、侵害が起きない保証にはしません。[S3]

本版の詳細は `SECURITY.md`。特に、標準SQLiteは平文、単一管理者、SSO/RBACなし、実収集器なし、ホストと鍵の同時侵害への対策なしであることを明示します。クラウドへ直接送信しない標準モードであっても、保存データやローカルの説明処理の機微性が消えるわけではありません。

## 9. 本番化の順序と受入条件

### Gate A: 読取専用の実ログ検証

対象企業の1接続経路、1認証基盤、1ファイル保管先に限定。収集できるフィールドと取得権限を確認し、入力契約へ正しく変換する。署名または収集経路の認証、収集心拍、遅延・欠損・再送・時計ずれを測る。実行権限は渡さない。

受入条件: 正常業務の代表的な期間・作業を含むログで検知を再生でき、担当者が根拠と業務上の正当性を判定できる。欠損を正常に見せない。評価母数と期間を記録し、検知率・誤検知率の分母を明示する。

### Gate B: 対応計画を実運用に適合

対象機器のバージョン・API・制限、セッション失効の影響、緊急保守の例外、失効後の復旧を検証。SSO/RBAC、承認者分離、秘密管理、外部監査保管を実装する。

受入条件: 実行前のプレビューで対象と影響を確認でき、期限切れ・入力更新・権限不足・二重承認・実行APIエラーを確実に扱う。検証環境でのみ実操作し、成否を別途照合する。

### Gate C: 限定的な実対応

承認済みの対象・操作から開始。分析面に管理資格情報を渡さず、実行面は短期の必要最小権限を使用する。自動遮断の導入は最後に判断し、最初から目標にしない。

受入条件: 復旧演習、誤検知時の業務影響評価、独立したセキュリティレビュー、負荷・障害・継続運用試験を完了。担当者が停止でき、実行された内容を第三者が追跡できる。

## 10. OSSと事業をつなぐ仮説

OSSに向く部分は、正規化スキーマ、検知ルール、再生用シナリオ、対応ポリシーの仕様、ローカルUIです。デモは「ログを読み込むと、一つの事案・根拠・次の確認までつながる」体験に絞ります。スターの数や話題性を保証するものではありません。

商用化候補は、顧客環境に合わせた収集器、監査・認証基盤、複数組織管理、運用支援、更新・サポート、実機ごとの対応連携です。汎用の無料検知器を課金壁の理由にはせず、接続と運用が正しく続くことに価値を置きます。

最初の検証商品案は「外部保守アクセスの読取専用診断」。価格の仮説は1社あたり初期5〜15万円、継続運用支援は月3〜10万円ですが、相場調査・顧客の支払意思を確認した値ではありません。取り扱うログ量と責任範囲が未確定なため、この数値を利益計画として使わないでください。

販売前に、候補3社程度で、現行の確認手順、誤検知を減らしたい作業、証跡作成の負担、利用できるログ、予算と委託範囲を聞きます。「AIがすごい」ではなく、事案の根拠に到達するまでの時間、確認漏れ、運用負担の改善が実証できるかで継続判断します。

## 11. 測定する指標

指標はモデルの文章の自然さだけではありません。ログ発生から収集・表示までの遅延、相関成立率、同一ユーザー・セッションの誤結合率、正常バックアップ時の誤検知、欠損表示の正しさ、参照IDの有効率、承認対象の一貫性、実行後検証率を測ります。

今回の合成データ試験は、実装した条件が動くことの検証です。実際の攻撃への検知率、False Positive Rate、MTTD/MTTRの改善、GSS事案の防止可能性を実証したものではありません。
