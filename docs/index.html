Anatomy of one case

Not a score. A case you can read.

The same screen holds the whole argument: what lined up, what is only a hypothesis, the evidence behind it, and the decision it still leaves to a person.

① WHAT LINED UP

Three signals, one case

An exposed, unpatched gateway → a privileged login that fails its conditions → a short burst of bulk file access, from the same user and session. Correlated, not stacked.

② THE REASONING, SPLIT

Confirmed / hypothesis / unknown

What the input confirms, what is only a hypothesis, and what is still unknown are kept apart — never blended into one confident sentence.

③ EVIDENCE ATTACHED

The event IDs, one click away

Every case carries the exact events behind it. “Related” and “a leak is confirmed” are shown as different claims, because they are.

④ THE DECISION STAYS HUMAN

No step runs on its own

The browser preview is simulation-only. The CLI can clear sessions for one narrowly validated Okta user only after two explicit approvals, then requires a matching System Log event; there is no automatic execution.

The number that started this

Everyone ships a “100 files in 5 minutes” rule.
Almost nobody publishes what it costs.

So we measured ours — on 18.8 days and 85,509 events of synthetic but realistic business activity: nightly backups, analyst bursts, a migration day, a search-indexing service, a weekly antivirus sweep, an eDiscovery pull, a batch ETL job, and approved vendor maintenance on a personal laptop.

RuleAlertsTrue positivesFalse positives
AS-003 — bulk file access, on its own 1031102
AS-004 — exposed gateway + privileged login + bulk access 110

Raising the threshold until the bulk rule goes quiet also stops it detecting the incident. We swept 21 threshold and window combinations: every configuration with zero false positives also missed the planted breach.

That asymmetry is the entire product thesis. Volume on its own is not a signal — a backup job looks identical to an exfiltration. A path is.

As metrics on ~75 synthetic days: AS-004 (correlation) reaches precision 1.00, F1 1.00, 0 FP/day; the bulk rule alone sits at precision 0.003. Quick start

No pip install. No API key. No cloud account.

Python 3.11 or newer is the only requirement. It binds to 127.0.0.1 with a fresh token each run.

git clone https://github.com/FORIFOR/AISecure.git && cd AISecure
python3 -m aisecure serve --demo

# Read your own logs — read-only, nothing is written back to the sources
python3 -m aisecure import \
  --source generic-auth-csv=auth.csv \
  --source generic-file-access-jsonl=access.jsonl \
  --out snapshot.json --quality quality.json

# Measure what a threshold costs on normal business activity
python3 -m aisecure baseline --days 5 --users 40 --out normal.json
python3 -m aisecure evaluate normal.json incident.json --sweep --out report.md
01 / COLLECT

Allowlisted fields only

CSV and JSON Lines are mapped through a declarative profile that can only name fields on an allowlist. A profile that imports file contents or credentials cannot be written. Values that cannot be read stay null — never false.

02 / DETECT

Deterministic and tunable

Exposure, privilege reachability and behaviour combine into a priority. Thresholds are configuration, hashed and written to the audit chain, so nobody quietly turns the sensitivity down.

03 / DECIDE

The human holds the authority

Each case separates observed from hypothesis from unknown, carries its evidence IDs, and states the business impact before anyone approves anything.

What it will not do

Written first, on purpose.

A security tool that only lists its strengths is not telling you enough to trust it.

  • The browser preview does not monitor. It analyses a snapshot you hand it. The CLI can poll local sources or an authenticated Okta System Log window.
  • It does not generally enforce. The only live response path is a narrowly scoped Okta session clear after two explicit approvals, with System Log verification. VPN, gateway and file-server controls are not implemented.
  • It does not confirm a leak. “These files were read” and “this data left the building” are shown as different claims, because they are.
  • No LLM decides anything. Detection is deterministic. The optional local model writes supplementary prose, gets no tools and no raw logs, and every reference it makes is checked before display.
  • Unknown is never “safe”. A field that could not be read is counted as unknown, not assumed benign.

A self-review found and fixed four detection-evasion defects in the import boundary before release — including one where choosing a device name could silently overwrite another asset's exposure status. It is not a third-party audit. Read the review →

When the input is broken or ambiguous

How it fails matters more than how it demos.

A tool is only trustworthy once you know what it does with a bad row, an unreadable value, or a case it cannot resolve. Here it fails loudly and safely — never with a quiet, confident, wrong answer.

MALFORMED ROW

Skipped with a reason, not dropped

A row it cannot parse is counted and given a reason in the quality report (rows_skipped, skip_reasons) — never silently discarded, never coerced into a value that changes a verdict.

UNREADABLE VALUE

Stays unknown, never “safe”

A field that cannot be read is kept as unknown — not false, not a benign default. Unknown never quietly becomes safe.

HOSTILE INPUT

Refused — never a crash or a leak

620 fuzzed import cases and 200 fuzzed HTTP requests: malformed and adversarial input is refused with a declared error, and no response leaks a stack trace or an internal path. One fuzz run found a real defect — a far-future timestamp poisoning the snapshot — now fixed.

AMBIGUOUS CASE

No false success

“These files were read” and “data left the building” stay separate claims. A correlation is labelled a correlation — it never reports a confirmed breach it cannot prove.

This is the question an enterprise actually turns on — not “does the demo work?” but “what does it do when it breaks?” The self-review →

Status

v0.3.0 — a local integration prototype, honestly labelled.

Useful today for

Studying detection logic that is legible end to end. Rehearsing a triage and approval workflow (UI fully in English or Japanese). And measuring what a threshold costs before you deploy one.

Not implemented

Direct VPN/file-server collectors, KEV and vendor advisory matching, SSO and RBAC, encryption at rest, external audit storage, recovery workflows and production deployment. Real-org validation is still required.

Where this sits: integration prototype (L1→L2) — you can evaluate it locally, poll bounded Okta System Log windows, and exercise a two-approval session response with verification. It is not a production (L3) control: real-org validation, SSO/RBAC, encryption at rest, external audit storage, recovery and an independent review are still open. The readiness checklist →

The next milestone is not more features. It is getting one organisation's real authentication, gateway and file-access logs through the importer, and measuring the false-positive rate over a period where nothing happened.

Built in response to the September 2026 disclosure of unauthorised access to Japan's Government Solution Service, where a Medium-rated, already-published vulnerability was exploited before the patch was applied and a maintenance account read a large number of files — precisely the case a CVSS-ordered queue handles badly. Nothing here reconstructs that incident; all bundled data is synthetic. Sources →
