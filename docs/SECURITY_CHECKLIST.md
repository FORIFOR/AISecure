# 実運用セキュリティ検証チェックリスト

「AI Secure は実運用でセキュアか」という問いに、正直に答えるための地図です。各項目に **状態** と **誰が検証すべきか** を付けています。ここでの「済み」は *この設計が主張する境界について、合成データと自動テストで確認した* という意味であり、**「本番として安全」を第三者が証明したという意味ではありません**。関連: [SECURITY.md](../SECURITY.md)（脅威モデル）・[SECURITY_REVIEW.md](SECURITY_REVIEW.md)（実施済みの検証と発見）。

**状態の凡例**：✅ 自己検証済み（合成データ・自動テスト） ／ ⚠️ 部分的・限定的 ／ ❌ 未実施 ／ 🔒 設計上スコープ外

---

## 1. 入力境界（未信頼データ）

| 項目 | 状態 | 検証者 | 根拠 / 次にやること |
|---|---|---|---|
| 取り込みが許可リスト外の項目を持ち込まない | ✅ | 開発 | `test_connectors` / `test_fuzz`（620ケース） |
| 読めない値が「安全」に化けない（不明のまま） | ✅ | 開発 | 同上。`false`/`0` への置換なし |
| 1行の異常（制御文字・ID衝突・未来日時・非有限数）で全体が落ちない | ✅ | 開発 | `test_fuzz` で発見した未来日時の欠陥を修正済み |
| タイムゾーンを推測しない | ✅ | 開発 | 明示なしは行を読み飛ばす |
| 実ログ形式での取り込み（Okta/Entra/Windows等の実エクスポート） | ❌ | 導入先・テスター | 実データで列名・時刻書式・文字コードを検証 |
| 変更されたログ書き出しの継続監視（`watch`） | ⚠️ | 開発・運用 | CSV/JSONLを再読込するポーリング。Okta System LogのHTTPS直接監視も実装済みだが、心拍・実組織E2E・他の直接コネクタは未検証 |
| 巨大入力・長期運用でのメモリ/資源上限 | ⚠️ | 開発・運用 | サイズ/行数/フィールド上限あり。実負荷は未測定 |

## 2. 通信・HTTP境界

| 項目 | 状態 | 検証者 | 根拠 / 次にやること |
|---|---|---|---|
| 127.0.0.1 限定・Host/Origin/クロスサイト検証・CORSなし | ✅ | 開発 | `test_http` / `test_http_fuzz`（200ケース） |
| 不正リクエストでクラッシュ・内部情報漏洩なし | ✅ | 開発 | `test_http_fuzz`：トレースバック/内部パス非漏洩 |
| 起動ごとのトークン認証、URLクエリ認証を受け付けない | ✅ | 開発 | `test_http` |
| CSP・frame拒否・no-store・nosniff | ✅ | 開発 | ヘッダをテストで確認 |
| **本番用HTTP基盤（TLS、レート制御、セッション、リバプロ信頼境界）** | ❌ | 本番設計 | 標準 `http.server` は本番非対応。置き換え前提 |
| 一般公開・トンネル・ポート転送での運用 | 🔒 | — | 設計上サポートしない（ローカル専用） |

## 3. 認証・認可

| 項目 | 状態 | 検証者 | 根拠 / 次にやること |
|---|---|---|---|
| API はトークン必須（全エンドポイント） | ✅ | 開発 | `test_http_fuzz` の認証強制テスト |
| 承認フロー（確認文字列・理由・期限・二重承認・改ざん拒否） | ⚠️ | 開発 | シミュレーションはUI、実操作はCLIの二者確認ラベル。SSOでの本人性は未実装 |
| **SSO / RBAC / 四眼原則（別担当者承認）** | ❌ | 本番設計 | 単一管理者前提。多者承認は未実装 |

## 4. 暗号・機密

| 項目 | 状態 | 検証者 | 根拠 / 次にやること |
|---|---|---|---|
| 識別子の仮名化（保存前に鍵付きHMAC） | ✅ | 開発 | DB・品質レポートに生値が残らないことを実測 |
| 監査チェーンの改ざん検出（鍵付きハッシュ連鎖） | ✅ | 開発 | 改変・末尾削除の検出テスト |
| **保管時暗号化（SQLite平文の解消）** | ❌ | 本番設計 | 標準ライブラリにAESなし。依存追加か本番ビルド分離が必要（[SECURITY.md](../SECURITY.md) 参照） |
| **鍵管理（KMS・ローテーション・分離保管）** | ❌ | 本番設計 | 現状は同一ディレクトリにローカル鍵 |
| ホストと鍵の同時侵害 | 🔒 | — | 脅威モデル上の対象外 |

## この製品を「試す/導入検討する」人へ

- **いま安全に試せること**：ローカル・オフラインでの動作確認、検知ロジックの精査、`watch` によるログ書き出しの継続監視、承認フローのリハーサル、モックレスポンダーへの署名要求テスト。実際のログ・秘密は入れずに評価できます。
- **導入前に必ず必要なこと**：上表の ❌ のうち、貴組織に関わる項目（実ログでの誤検知測定、SSO/RBAC、保管時暗号化と鍵管理、独立監査、第三者レビュー/ペンテスト、法令・保持ポリシー）。
- **報告のお願い**：試して気づいた不備は [Issue](https://github.com/FORIFOR/AISecure/issues) へ。実ログ形式が取り込めない・正常業務が誤検知になる、といった報告が最も価値があります（実ログや秘密は貼らないでください）。

このチェックリストは検証の「地図」であり、安全性の保証ではありません。実運用の安全性は、実環境・第三者検証を通して初めて言えます。
